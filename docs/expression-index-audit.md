# Expression Index & Full-Text Search Coverage Audit

**Verdict: PARTIAL — 14 gaps identified (generated `search_vector` + GIN does NOT cover the app's query-side expressions).**

> Scope: Static audit of query-side expressions (`WHERE`, `JOIN`, `ORDER BY`, regex/pattern matching, generated columns, and GIN/btree/trigram indexes) across `src/` query helpers and `supabase/migrations/*.sql`. No SQL migrations or database changes are included in this PR.

---

## Executive Summary

The database audit flagged expression indexes as `PARTIAL` because `supabase/migrations/20261001_filter_upgrades.sql` introduced a stored generated `tsvector` column (`jobs.search_vector`) with `jobs_search_vector_idx USING GIN (search_vector)` plus three `pg_trgm` GIN indexes (`title`, `company`, `location`) instead of functional btree expression indexes.

Re-deriving every query actually issued by the application and SQL views/RPCs shows that **`search_vector` + GIN does not cover app search behavior, and 14 concrete query-side expressions remain uncovered (`GAP`)**:

1. **`jobs.search_vector` has 0 callers in `src/`**: No API route or service calls `.textSearch("search_vector", ...)`. Free-text search in `src/app/api/jobs/search/route.ts` uses multi-column `.ilike("%q%")` including `description.ilike.%q%`, which PostgreSQL cannot route through `tsvector` GIN and which lacks any trigram GIN on `description`.
2. **Array GIN on `categories` vs. scalar `category` queries**: `jobs_categories_gin_idx` indexes `jobs.categories` (`TEXT[]`), whereas all query helpers (`search/route.ts`, `service.ts`, `api/jobs.ts`, `JobRadarGlobe.tsx`) filter the scalar `category` (`TEXT`) column with `.eq`, `.in`, and `.ilike`.
3. **Unindexed `jobs` text/prefix/equality predicates**: `company_slug ILIKE`, `salary_text ILIKE '<prefix>%'`, `source ILIKE`, `source_type = ...`, `job_type ILIKE` (and standalone `job_type = ...`), `country = ...`, short 2-char regex `title.imatch.\yAI\y` (`pg_trgm` yields no trigrams), `created_at >= todayMidnight`, and composite keyset ordering `(verified DESC, posted_at DESC NULLS LAST, id DESC)`.
4. **Related tables & join normalization**: `LOWER(TRIM(j.company)) = LOWER(TRIM(c.name))` in `worldwide_company_counts` has no functional btree index (mitigated on read by MV materialization in `20261101_lock_scraper_metadata.sql`, unindexed during refresh); `companies.name IN (...)` in `src/app/api/ticker/route.ts` has no index on `companies(name)`; and `email_suppressions.email ILIKE norm` in `src/lib/events/failedEvents.ts` bypasses both `idx_email_suppressions_lower_email ((lower(email)))` and `email_suppressions_email_key (email)`.

## Explicit Gaps Summary (14 Gaps)

1. **`jobs.title:imatch` (`title.imatch.\yAI\y`)**: `idx_jobs_title_trgm` (`gin_trgm_ops`) extracts zero 3-character trigrams from the 2-character regex `\yAI\y` in `search/route.ts` and `service.ts` (similarly 1–2 char patterns like ` ai ` or `sr.`).
2. **`jobs.description:ilike` (`description.ilike.%...%`)**: `search_vector` + `jobs_search_vector_idx` (`20261001_filter_upgrades.sql`) is dead DDL because zero app files invoke `.textSearch()`. Meanwhile, `/api/jobs/search` issues leading/trailing-wildcard `description.ilike`, which cannot use `tsvector` GIN and lacks a trigram index.
3. **`jobs.category:eq_in_ilike`**: `jobs_categories_gin_idx` indexes array column `categories TEXT[]`, while every app filter queries scalar `category TEXT` (`eq`, `.in()`, `ilike`). Scalar `category` has zero indexes.
4. **`jobs.company_slug:ilike`**: `/api/jobs/search` queries `company_slug.ilike.%...%` when filtering by company; `jobs.company_slug` is completely unindexed.
5. **`jobs.salary_text:ilike`**: `src/lib/api/jobs.ts` runs multi-prefix `salary_text.ilike.$100%...` OR clauses; only numeric `salary_min` is indexed (`jobs_salary_min_idx`).
6. **`jobs.job_type:eq_ilike`**: `job_type.ilike.%full%` / `%contract%` / `%part%` / `%intern%` and standalone `job_type.eq.*` cannot efficiently use `jobs_active_verified_idx (country_code, seniority, job_type)` when `country_code`/`seniority` are unconstrained or when leading wildcards are used.
7. **`jobs.source:ilike`**: `source.ilike.%greenhouse%` / `%board%` in `/api/jobs/search` cannot use the `(source, source_job_id)` unique btree index.
8. **`jobs.source_type:eq`**: `source_type.eq.*` in `/api/jobs/search` has no index on `jobs.source_type`.
9. **`jobs.country:eq`**: `country.eq.<countryName>` in `src/lib/api/jobs.ts` has no index on `jobs.country` (`jobs_country_code_idx` only covers `country_code`).
10. **`jobs.created_at:gte`**: `/api/stats` runs `.gte("created_at", todayMidnight)` on `jobs_public` (`jobs`) on every uncached public stats refresh with zero index on `jobs.created_at`.
11. **`jobs.keyset_sort:verified_posted_at_id`**: `/api/jobs/search` and `service.ts` order by `[verified DESC,] posted_at DESC NULLS LAST, id DESC`; `jobs_posted_at_idx` is only single-column ascending `(posted_at)`, forcing sort / heap work on large filtered result sets.
12. **`jobs.company_lower_trim_join:expr`**: `worldwide_company_counts` joins on `LOWER(TRIM(j.company)) = LOWER(TRIM(c.name))` without a functional btree index on either side (mitigated on read by MV materialization in `20261101`, still unindexed on refresh).
13. **`companies.name:in`**: `/api/ticker` expands company names into case variants and runs `.in("name", ...)` against `public.companies`, which only indexes `(id)` and `(slug)`.
14. **`email_suppressions.email:ilike`**: `isEmailSuppressed` in `src/lib/events/failedEvents.ts` calls `.ilike("email", norm)`. Neither `idx_email_suppressions_lower_email ((lower(email)))` nor `email_suppressions_email_key (email)` serves SQL `ILIKE` on an already trigger-lowercased column (contrast with `dailyDigestCron.ts`, which correctly uses exact `.in("email", chunk)`).

## Additional Observations

- **Pending-apply migrations**: `20261106k_autocomplete_pg_trgm.sql` (redundant `jobs_title_trgm_idx`), `20261106n_covering_index_jobs_list.sql` (`jobs_active_list_covering_idx`), and `20261107a_jobs_role_dedupe.sql` (`jobs_role_key_active_idx`) exist in `supabase/migrations/` with manual-application notices (`STATUS: NOT APPLIED` / manual execution required). Live production planners only benefit from them once applied in Supabase.
- **`jobs_public` view predicate vs. partial indexes**: `20261010_lock_paid_jobs_data.sql` defines `jobs_public` with `WHERE is_active = true OR status = 'active'`, while `20261001_filter_upgrades.sql` partial indexes use `WHERE status = 'active'` or `WHERE is_active = true AND status = 'active'`. Callers that omit `.eq("status", "active")` (such as `suggest/route.ts` on `jobs_public` or `dailyDigestCron.ts` on `jobs`) cannot satisfy stricter partial index predicates unless `.eq("is_active", true).eq("status", "active")` is also asserted (which `/api/jobs/search`, `service.ts`, `stats`, and `radar` explicitly pass).
- **Date truncation**: No code path or migration uses `DATE_TRUNC` in any `WHERE` or `ORDER BY` predicate (`stats/route.ts` computes UTC midnight in JS and passes an ISO timestamp to `.gte("created_at", ...)`).
